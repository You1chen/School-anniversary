# 暨南大学校史问答库 · 数据层说明

> 用途：卓越杯B赛道"百廿校史AI讲解员/数字人"项目的**问答数据层**，对应《极简版设计思路》里的"检索层"输入。
> 建立：2026年10月6日｜**19 个分片、328 条、覆盖 1497 种问法**（`verified` 180／`partial` 135／`conflicting` 12／`unverified` 1）。
> 本文件只讲**怎么读写数据**，不讲检索算法与生成层实现。

---

## 一、两层分离：史料层 / 问答层

```
暨大史料\        ← 史料层（证据）：官网原文照录、图片与图注，**只增不改**
知识库\          ← 问答层（产品数据）：从这里抽的问答对，**可自由增删改**
```

**为什么分开**：史料是"证据"，一旦改动就无法溯源；问答是"表述"，需要反复打磨。两层用 `local_refs`（指向史料文件）和 `evidence`（原始语句片段）连起来——**改答案时不需要动史料，改史料时也不影响问答的字段结构**。

## 三、一条记录长什么样

```json
{
  "id": "XQ-001",
  "question": "暨南大学是什么时候创办的？",
  "aliases": ["暨南大学哪一年建校", "暨南大学的前身是什么"],
  "answer": "暨南大学的前身是1906年……",
  "source": "暨南大学120周年校庆专题网·校史沿革",
  "source_url": "https://120th.jnu.edu.cn/xsyg/main.htm",
  "evidence": "学校的前身是1906年清政府创立于南京的暨南学堂……",
  "local_refs": ["00-校史总览与官方资源索引/校史沿革-官网全文.md#一、沿革主干"],
  "period": "1906-1923",
  "type": "史实",
  "keywords": ["1906", "建校", "暨南学堂"],
  "status": "verified",
  "caveat": "…（可选）",
  "updated": "2026-10-06"
}
```

| 字段 | 必填 | 作用 | 什么时候改它 |
|---|---|---|---|
| `id` | ✅ | 稳定标识 | **永不改、永不复用**（详见第五节） |
| `question` | ✅ | 主问法（最自然的那一种） | 发现更常见的问法时替换，旧问法降级进 `aliases` |
| `aliases` | | 同义问法数组，检索时与 `question` 同等对待 | 用户问法没命中时**只加问法，不改答案** |
| `answer` | ✅ | 答案正文 | 口径变化或需要收短/加长时 |
| `source` | ✅ | 人可读出处，**必填**（设计思路硬要求） | 换权威出处时 |
| `source_url` | | 官网/来源链接 | 同上 |
| `evidence` | | 支撑答案的**原文片段** | 便于日后核对与改写；改写答案时同步更新 |
| `local_refs` | | 本地史料位置 `文件夹/文件.md#小节` | 离线溯源用 |
| `period` / `type` / `keywords` | | 过滤与召回辅助 | 用于"只看某时期""只看人物类" |
| `status` | | `verified` / `partial` / `conflicting` / `unverified` | 核实进展变化时 |
| `caveat` | | 使用时必须一并说明的注意事项 | 发现口径冲突、官网笔误、数据时点时 |
| `name` | | 地图区域在页面上的显示名（目前只有 MP 片用：热点浮层的标题、侧栏的 `h3`） | 地标改名时。**名字只存这一份**，页面不另抄一遍；少了它 `build.mjs` 会中止打包（否则浮层只剩一个光秃秃的编号） |
| `caption` | | 配图的原始图注（目前只有 MP 片用：地图区域侧栏那张史照的说明） | 换配图时；没有配图就留空串 |
| `see_also` | | 相关条目的 id 数组（MP 片用它指回持有本体史实的 DM 条目，页面上的"深入"按钮据此跳转） | 相关条目增删时；**指向不存在的 id 会让 `build.mjs` 中止打包** |

> **`status` 的用法**：`verified` 直接答；`partial`/`conflicting` 必须**连同 `caveat` 一起输出**（不要替用户选一个说法，也不要藏起来）；`unverified` 默认不进答案，只作检索线索。
> 首批 37 条中 `verified` 33 条、`partial` 4 条——这 4 条正是"校徽各版差异""校徽色值""二三四版校歌""三落三起对应"，都属于**官方本身没讲清**的地方。

## 四、为"方便日后增删改"做的八处解耦

| # | 解耦点 | 效果 |
|---|---|---|
| 1 | **两层分离**：史料层只增不改，问答层随便改 | 改文案不会破坏溯源链 |
| 2 | **一片一文件**：按时期/专题分片 | 两人同时改不同专题不会冲突；删一个专题就是删一个文件 |
| 3 | **manifest 驱动**：应用只认清单 | 加分片不改代码；分片顺序、文件名可自由调整 |
| 4 | **一问多问法**：`question` + `aliases` | 答案只存一份——**改一处，所有问法同时生效**，不会出现"同一个问题两个答案不一致" |
| 5 | **答案与证据分离**：`answer` / `evidence` / `local_refs` | 出处换了不用重写答案；答案改了能立刻回查原文 |
| 6 | **状态与答案分离**：`status` / `caveat` | 没核实透的内容也能先入库，但**不会被误当成定论答出去** |
| 7 | **兜底与数据分离**：`fallback.json` | 改话术、加引导问法不必碰任何知识条目 |
| 8 | **人设与数据分离**：`persona.json` | 改口吻、改自称不必碰任何知识条目。**它是全库唯一不写成分片的同类文件**：分片会被 `build.mjs` 汇进 `items` 参与检索打分，人设一旦进去，问「你是谁」时它就去挤候选名额，还会让 `eval.mjs` 的 185 条留出集基线变动 |

## 五、编号规则（重要）

- 格式：**`分片码-三位序号`**，如 `XQ-001`。
- **ID 一经分配，永不复用、永不重排。**
- 删除条目后，它的编号**就空着**，新条目用当前最大号 +1。
  例：删掉 `NJ-005`，下一条新条目是 `NJ-011`，不是 `NJ-005`。
- 为什么：ID 是检索日志、测试用例、外部引用的锚点，重编号会让所有引用静默失效。
- 分片码在 `manifest.json` 的 `planned_shards` 里登记（目前是空数组，历史上预告过的分片都已落地并入 `shards`）。新增分片取一个未被占用的两字母码，并同时改三处：新建 `shards/<码>-<名>.json`、在 `manifest.shards` 里加一行、在第七节校验一次。

## 六、增 / 删 / 改 的标准动作

### 加一条
1. 决定它属于哪个分片（不确定就选最接近的时期/专题片）。
2. 取该片当前最大序号 +1 作为 `id`。
3. 先写 `evidence`（原文片段），再写 `answer`——**顺着证据写答案，不要反过来**。
4. 填 `source`（必填）。若官网有链接，填 `source_url`。
5. 补 `aliases`：把你想到的 2–5 种问法都写进去。
6. 官方没讲清的地方：**不要圆场**，把 `status` 设为 `partial`/`conflicting`，把不清楚的点写进 `caveat`。
7. 改该分片头部 `count`、`updated`，并在 `manifest.json` 对应分片更新 `count`。
8. 跑一次校验（见第七节）。

### 改一条
- 只改问法 → 只动 `question`/`aliases`，**答案不动**。
- 只改表述 → 只动 `answer`，`evidence` 保持原文不动。
- 改了事实口径 → `answer` + `evidence` + `caveat` 三处一起看，并更新 `updated`。
- 换更权威的出处 → `source`/`source_url`/`local_refs` 一起换。

### 删一条
- 删掉整个对象，**保留编号空缺**，不要重排后面条目。
- 同步改分片 `count` 与 manifest 的 `count`。
- 如果是"整片作废"，直接从 `manifest.shards` 移除该行（文件可留在磁盘上作历史）。

## 七、交付前校验清单

每次改动后确认：

1. JSON 可解析（每个分片文件都能 parse）。
2. `id` 全库唯一。
3. 必填字段齐全：`id` / `question` / `answer` / `source`。
4. **同一问法（`question` + `aliases`）不指向两条记录**——否则检索会随机命中。
5. 每条答案的 `source` 非空，且能在 `暨大史料/` 里找到对应内容。
6. 分片 `count` 与 `manifest.json` 里的 `count` 与实际条目数一致。
7. `status` 非 `verified` 的条目都有 `caveat`。
8. 重新生成 `审阅稿.md`（它只是给人看的镜像，**不是数据源**）。

以上 1–7 项已固化为脚本。改完数据跑一句即可——默认只校验并重新生成审阅稿，**不改动任何数据**；加同步参数才把实际条目数写回 `manifest.json`：

```
node 知识库\校验.mjs                  # 只校验 + 重新生成审阅稿
node 知识库\校验.mjs --sync-manifest   # 额外把各分片条目数写回 manifest.json
```

等价的老脚本（PowerShell，需要执行策略允许跑脚本；本机默认 Restricted，所以一直没跑成过）：

```
powershell -NoProfile -ExecutionPolicy Bypass -File "知识库\校验并生成审阅稿.ps1" -SyncManifest
```

> **两个脚本是一套规则的两种实现，改校验规则时必须一起改。** Node 版的存在意义是让本机也能校验；两者产出的 `审阅稿.md` 内容完全相同，只有换行符不同（`.ps1` 的 `WriteAllLines` 写 CRLF，Node 版写 LF，跟磁盘上现有那份一致，免得整个文件被换一遍行尾）。

> 踩过的坑：Windows PowerShell 5.1 按 ANSI 解码 `.ps1`，脚本文件必须带 **UTF-8 BOM**，否则中文全部乱码并报语法错。本脚本已带 BOM。

> 截至 2026-10-08 的实测结果：**19 片 / 328 条 / 1497 种问法 / 重复 ID 0 / 缺字段 0 / 问法冲突 0 / 计数一致**。

## 八、与《极简版设计思路》接口的对应

设计思路约定 `ask(question) -> {answer, source, matched}`：

| 返回值 | 数据来源 |
|---|---|
| `answer` | 条目的 `answer`；若 `status` 为 `partial`/`conflicting`，应把 `caveat` 一并拼入 |
| `source` | 条目的 `source`（必填，天然满足） |
| `matched` | 命中任一 `question`/`aliases` 为 `true`；否则 `false` |
| `matched=false` 时 | 取 `fallback.json` 的 `fallback.no_match`，并从 `hints.suggested_questions` 里带出引导问法 |

**上 `ask()` 之外不要加新接口**：扩充分片、改字段内容都不影响该签名；将来接入 LLM 生成层时，只需把 `answer` 从"直接返回"改成"作为检索上下文喂给模型"，数据结构不动。
